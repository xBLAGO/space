# Personal lifecycle and optional public commitments

Draft. No immutable personal ledger or on-chain deployment is authorized.

## Data classes / retention boundaries

| Class | Location / default | Correction, erasure and restore |
|---|---|---|
| Conversation/memory/private asset content | Existing protected domain store / future reviewed per-user vault; no transcript copy in UEL | Same user correction/forget/delete/retention; erase source refs, summaries/embeddings/cache, queued exports and decrypt capabilities as applicable |
| Local operation/provenance metadata | Restricted local index, minimal fields with approved TTL | Metadata also can be personal; unlink/delete unnecessary fields. Keep only required pseudonymous denials until backup retirement is proved |
| Critical denial/control state | Existing original journal/head/key/witness, independently retained | Not ordinary app backup data. Never rollback/reinitialize to restore access. UEL must reconcile it before serving personal content |
| Recipient disclosure package | Exact purpose/audience/version consent, minimized/encrypted through reviewed mechanism | Receiver-scoped revocation/erasure notices, durable purge ACK; external physical deletion not guaranteed by signature |
| Public aggregate release | Separate reviewed schema, purpose and public-irreversibility consent, privacy budget/re-identification review | Retraction/correction releases and current-status pointers; previously public copies cannot be made private again |
| Public blockchain anchor | Root of **approved public releases only**, minimal publisher/batch metadata | Immutable old root remains. It is not a latest-authorization service, proof of truth, private data erasure or key recovery |

Current code does not provide general per-user encryption/portable crypto-shredding for every table. A future vault uses reviewed AEAD/key lifecycle, not homemade encryption. Deleting a key is not proof all plaintext/log/provider/browser/backup copies disappeared. All existing G04 external inventory/policy/custody gaps remain.

## Withdrawal and erasure protocol

1. Authenticate person through existing local method or independently verified portable controller authority; distinguish withdrawal of one grant, correction of one assertion, registry-only erase and full account deletion.
2. Atomically fence current scope/version and in-flight recipient contexts; enqueue durable deny under existing controls before success. Owner context fencing alone is insufficient once shared payloads enter other agents' LLM contexts.
3. Remove authorized target content and derivatives: local vault/record links, source exports, model context caches, embeddings, pending worker results and delivery queues. Do not blindly delete lawful separate Help outcome evidence or silently retain it with personal text.
4. Retain minimally necessary authenticated tombstone/coverage information; no plain UID/biography/global personal hash in public evidence. Verify cross-merge lineage, quarantine ambiguous legacy ownership instead of guessing.
5. Send minimized authenticated withdrawal/purge notice to known recipients. Store pending vs acknowledged/unknown states. No false global-erasure success under partition; peer may be malicious or already have copied data.
6. Restore old app snapshot only with current original controls: apply denials before exposing content; drop unsupported positive state on mismatch, invalidate obsolete sessions/challenges/generations and preserve used IDs/frontiers. Missing control copies → UNKNOWN_RECOVERY.

An append-only provenance log is compatible with mutable/deleted **payload** only when references/linkage and retention are designed accordingly. Do not claim forever-retained event metadata is anonymous because it is hashed. Deleted data must not be regenerated by an LLM summary, a prior signed event, an anchor proof, a replayed export or key recovery.

## Public release barrier

No anchor of private event roots, even with salt/encryption advertised as automatic anonymization. Low-entropy values and timing/count relationships can re-identify; encrypted personal payload retained publicly also creates future-decryption risk. The release barrier produces a separate minimized aggregate whose disclosure is explicitly approved under a versioned policy.

That policy must define cohort/thresholds, suppression, schedule/padding, compatible unit/evidence coverage, differencing limits across successive releases, review authority and recipient/public purpose. A chosen k or a `privacy_approved=true` field alone is not proof. No such production policy or privacy mechanism is approved in this PR. No auto-anchor via chat or Agent.

Published fields may include only a random release ID, metric enum/rounded or suppressed value and reviewed release-policy reference. No participant, asset, Help, origin-event ref, exact private timestamp, location or per-person value. Public publisher identity may be stable, personal identity must not be. Even aggregate activity patterns require review.

## Merkle and anchor design

Use the tree hash convention of [RFC9162](https://www.rfc-editor.org/rfc/rfc9162), with a separately domain-separated **public release** leaf payload. The standard supplies tree hashing/proof concepts, not BLAGO authorization/privacy guarantees.

```
leaf_data = ASCII("BLAGO/UEL/0.1-lab.1/PUBLIC-LEAF") || 0x00 ||
            random_salt_32 || C(approved_public_release)
MTH([])   = SHA256(empty)
MTH([x])  = SHA256(0x00 || x)
MTH(D)    = SHA256(0x01 || MTH(D[0:k]) || MTH(D[k:n]))
# k = largest power of two strictly below n
```

Salt must be freshly random in an actual approved release; deterministic/zero salts in fixture examples are TEST ONLY. Domain prefix forbids interpreting a private-tree leaf as a public aggregate leaf. Proofs need leaf index/tree size, exact release bytes/salt, tree root, pinned publisher signature and chain-specific finalized inclusion proof. Verify all bindings, not a root screenshot or transaction URL alone. Merkle inclusion proves membership, **not completeness, truthful quantities, valid consent or current authority**. The current example tests hashes/schema distinction, not a complete inclusion/consistency verifier.

Future signed public checkpoint fields: profile/schema_hash, publisher_key, random batch_id, sequence, tree_size, root, previous_checkpoint_ref, release_policy_ref, approval_ref, intended_chain_network. Distinct CHECKPOINT/PUBLIC-ANCHOR signature domains; strict field sets and exact pinned schema hash. Same sequence/different root → equivocation; monotonic checkpoint with valid consistency proof, not trusted timestamp, advances the public frontier.

A future `EventAnchor` contract/program interface may accept that approved public checkpoint commitment, publisher authority and predecessor. On-chain storage only needs root/size/profile/policy commitments and publisher/batch chaining; no raw events/UIDs. Chain/network/finality/fee authorization and contract upgrade/governance policy remain decisions for separate reviewed PR. Solana is a possible existing architecture target, not an active network. No contract or wallet is created here.

Anchor receipts attest finalized inclusion under a selected chain's assumptions. They cannot reissue a mandate, settle a Help dispute, force a peer to erase, imply BTC backing, provide a global clock/order or restore deleted payloads. Revoking a previously published assertion yields a new current-status correction; prior roots remain historical and must never be used as fresh authorization. Offline/local operation must not require a founder-run chain indexer.

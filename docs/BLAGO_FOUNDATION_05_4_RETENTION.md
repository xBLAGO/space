# Foundation 05.4 — проект retention и legacy merge policy

Статус: **предложение к утверждению**, не правовое заключение и не объявление
соответствия законодательству. Сроки ниже не активируются автоматически этим PR.
До утверждения владельцем данных и применимых обязательств пилот с финансовыми
зависимостями/непроверенными legacy merges не открывается.

## Завершённые экономические операции

Завершённость определяется существующим протоколом: подтверждённое исполнение и
существующие экономические события/contribution. Статус нельзя менять ради
удаления аккаунта. Не меняются суммы, валюты, exchange rate, event ID,
последовательность, balances или правило единственного contribution.

Предлагается минимальный reconciliation ledger на 180 дней после завершения
или закрытия последнего спора (берётся более поздняя дата). До применения
владелец подтверждает срок, цель, доступ и законные обязательства; для реальных
платежей потребуется отдельная оценка. Открытое обязательство/спор не считается
завершённой операцией и обрабатывается ответственным оператором до разрешения.
Это ограниченная операционная цель, не бессрочное сохранение всего профиля.

Минимум ledger: неизменяемый economic event ID, participant reference с
контролируемым сопоставлением, kind/status, amount/currency/rate и время.
Свободные заметки, история диалога, города, устройства, Telegram usernames,
session tokens и credential data не являются частью необходимого ledger.
Псевдонимизация не равна анонимизации. Нельзя просто обнулить FK и объявить
удаление выполненным, если reference всё ещё позволяет восстановить человека.

До реализации проверенного selective deletion workflow текущий account-delete
возвращает отказ при финансовых зависимостях. Оператор сообщает основание,
объём и срок удержания, предоставляет доступный personal export и регистрирует
запрос в ограниченном case register. Нельзя сообщать «аккаунт удалён» при отказе.
Разрешение исключения/правовой hold должно иметь владельца, основание, дату
пересмотра и уведомление участнику. После срока — отдельная проверяемая задача
минимизации/удаления с replay tombstones, FK/integrity и reconciliation tests.
Этот PR не добавляет такой экономический purge и не изменяет бизнес-правила.

## Backup, ключи и технические данные

Предлагаемая rolling retention application backups — 35 дней в зашифрованном
offsite storage с контролем доступа. Реестр обязан учитывать экспортированные,
ручные, DR и тестовые копии. Пока существует хотя бы одна разрешённая к
восстановлению копия, соответствующие privacy tombstones и необходимые ключи
нельзя уничтожать. После подтверждённого retirement всех способных вернуть
данные копий — дополнительный 35-дневный safety window и проверяемое решение
об уничтожении. Legal hold продлевает конкретные записи с явным основанием.
Это предложение требует утверждения и реальной storage lifecycle конфигурации.

Журнал не включается в обычный application backup; его зашифрованные DR bundles
и независимый checkpoint имеют отдельные custodians/retention. Wrapping key
не хранится рядом с bundle или на единственном основном сервере. Потеря ключа
или последнего witness блокирует restore. HMAC journal tags — персональные
псевдонимы, поэтому доступ ограничен, журнал не публичен и не отправляется LLM.
Нельзя очищать tombstones стандартным TTL технических событий.

Текущий технический cleanup 05.3 сохраняется: просроченные challenges/exchanges
и законченные sessions убираются по существующим TTL, без удаления финансовых
событий, dialogue, Telegram update dedupe или security journal. Privacy clear
теперь очищает response/error cache, сохраняя сам факт обработки update.
Необязательный activity collection остаётся выключенным; fingerprinting нет.

## Legacy merges

Достоверная alias lineage строится только по детерминированным записям исходных
account IDs, проверенным channel links и подтверждённому контролю обоих способов
доступа. Имена, похожий текст, IP, устройство и мнение LLM не являются proof.

При отсутствии `account_aliases` оператор сопоставляет доступные до/после merge
backup, timestamps, уникальные Telegram links и auth audit. Двусмысленность,
конфликт уникальности или отсутствие одного подтверждения → quarantine
конкретного case/копии; никакого автоматического объединения/полного стирания.
Недостаточно вручную дописать alias по просьбе текущего пользователя.

Исправление однозначного legacy case требует отдельного reviewed migration PR:
до/после manifests, проверка uniqueness/FK, transaction+rollback, immutable audit,
explicit user proof и повтор restore самого раннего разрешённого backup.
Shared economic records не удаляются по предполагаемой связи. Исторические
копии без доказуемых удаления/lineage исключаются из разрешённых recovery
sources; новый 05.4 marker не превращает их в проверенные копии.

Владелец утверждает политику и pilot scope; security reviewer проверяет
recovery evidence; отдельный custody operator подтверждает backup retirement.
Назначение этих ролей и сроки review — обязательное эксплуатационное действие,
не выполненное изменением исходного кода.

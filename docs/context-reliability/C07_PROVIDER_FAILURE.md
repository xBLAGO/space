# C07: несохранённая поправка при сбое провайдера

Baseline: exact `ca11f21cc5a0b7aecd60f9ea23063ed9eead4e5d`, PR #41.
Исправленный runtime: `51142f2294c8cdcbe23dabd23e9221ad790e5943`.
Синтетический локальный HTTP-стенд; HF и реальные устройства не используются.

## Воспроизведение и критерий

В сохранённой памяти — «Перми». Пользователь сообщает:
«Я больше не живу в Перми, теперь живу в Томске».
Управляемый provider выбрасывает `LlmProviderError(category='unavailable')`.

На baseline тест воспроизводимо завершается FAIL: ответ
«Сейчас не получается связаться. Твоё сообщение осталось в диалоге.»
не сообщает об отсутствии записи поправки. Это не доказательство сохранения
или потери данных у реальных участников: база создана заново для теста.

[Baseline evidence](evidence/C07-before.json): expected FAIL на чистом baseline.
[Исправленная версия](evidence/C07-after.json): PASS на чистом runtime SHA,
фактические тексты ответов всех трёх каналов. Source turn **11**, span **[40,46]**
выделяет «Томске» в успешно повторённой поправке; не ссылается на первую
неудачную попытку. Оба evidence содержат хэш теста и статус чистоты tracked tree.

| Шаг | Проверяемое поведение исправленной версии |
|---|---|
| Сбой при поправке | Явно сообщить: поправка о Томске не сохранена; в памяти по-прежнему Пермь |
| Следующий вопрос Web/Bot/Mini App | Все три объясняют различие сохранённой Перми и несохранённой поправки о Томске, даже пока provider недоступен |
| Переоткрытие SQLite/WebApp | Предупреждение не зависит от process-local состояния |
| Успешный явный повтор поправки | Сохранённый город — Томск; все три канала получают актуальный контекст и называют Томск |
| Источник | Проверенный owner-scoped user turn повторной поправки; точный span «Томске», а не первая неуспешная попытка |

## Механизм

Общий детерминированный parser личных фактов перенесён без изменения правил из
агента в `memory_policy.extract_personal_facts`. Публичный внутренний alias
`_extract_personal_facts` агента сохранён. Нового независимого parser нет.

При сбое генерации и изменении уже сохранённого города ответ строится локально
и прямо сообщает, что поправка не сохранена. Активная каноническая память
остаётся прежней; новых semantic records или candidate-фактов не создаётся.
Повтор не выполняется автоматически. Пользователь повторно присылает поправку.

Следующий scoped snapshot восстанавливает NOT_SAVED из существующих
`lifecycle_history_pairs`: пользовательская поправка + точный локальный ответ
о неуспехе. Обе стороны пары принадлежат тому же UID; проверяются roles,
retained history floor и несовпадение предложения с текущим сохранённым городом.
Это проекция намерения из истории, а не второе хранилище фактов или журнал.
`pending_corrections` отделён от `memory` и содержит source turn и NOT_SAVED.
LLM не может подтвердить запись своей фразой. Подтверждённое самозаявление
по-прежнему не означает независимой проверки физического места проживания.

Узкий вопрос «Где я живу?» при наличии такой поправки получает локальный
проверяемый ответ. Вопрос об источнике города также отмечает несохранённую
поправку. После успешной записи прежний history barrier исключает старую
попытку, а источник связывается с новой user-репликой в общей транзакции.

Ограничения: только поддерживаемые поправки города; последние 64 доступные
атомарные пары после privacy floor. История может быть очищена или удалена
retention: тогда проекция несохранённого намерения исчезает, не становится
долговременной памятью. Произвольное извлечение старых тем не реализовано.
Без таблицы проверенных пар неподтверждённый pending не реконструируется.

## Приватность и G09

Новых таблиц, миграций, checksum или endpoints нет. UID не берётся из текста.
Модель не получает новых полномочий; read-only ответ проходит обычный
`Generation.commit`: revision/epoch CAS и запись пары — в одной транзакции.
При удалении между подготовкой предупреждения и commit ответ отклоняется.
Во время LLM write transaction не удерживается.

Удаление факта повышает retained floor, поэтому pending не возвращает Томск
в контекст после удаления и восстановления старого backup. Очистка истории
удаляет источник pending; разрешения и факты из него не восстанавливаются.
Завершённая запись либо подтверждённое повторение прежнего города вытесняют
неуспешную попытку. До commit ответ с обещанием сохранения не публикуется.

## Запуск

В изолированной копии с безопасными Python/SQLite из RUNBOOK:

```sh
PYTHONPATH=.:src python -m unittest \
  tests.test_agent_context.AgentContextTests.test_C07_failed_correction_is_explicit_and_shared_across_channels \
  tests.test_agent_context.AgentContextTests.test_C07_pending_correction_removed_by_deletion_and_old_backup_restore \
  tests.test_agent_context.AgentContextTests.test_C07_pending_reply_rejected_if_fact_deleted_before_commit \
  tests.test_agent_context.AgentContextTests.test_C07_reaffirmed_old_city_supersedes_pending_without_automatic_retry -v
```

HTTP использует disposable localhost и `Secure=false` только внутри теста.
После Telegram linking выполняется штатный повторный login: отзыв старой сессии
не отключается. Mini App проходит существующий challenge и синтетический
подписанный initData; это не запуск физического Telegram WebView.

Ответы после успешного повтора выдаёт контролируемый provider по реальному
scoped context. Это проверка wiring и состояния, не оценка живой Qwen.
Физические устройства и живой provider — NOT EXECUTED; реальный пилот — NO-GO.

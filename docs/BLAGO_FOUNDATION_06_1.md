## Natural Conversation Engine

`core/conversation.py` вычисляет **временную подсказку о текущей реплике**, а не
диагноз, профиль, экономическую задачу или согласие. Поддержаны размышление,
обычный разговор, эмоция, фактический вопрос, потребность, предложение ресурса,
явная просьба, отказ и изменение намерения. Неоднозначное сообщение остаётся
обычной беседой. Есть контекст предыдущего пользовательского намерения и признак
продолжения существующего разговора; предыдущая цель не получает приоритет над
новым отказом/изменением мнения.

Классификатор — экономные локальные cues, а не дополнительная LLM. Его подсказка
может быть ошибочной: основной вызов видит сообщение и историю и получает прямую
инструкцию учитывать их смысл. Метка не публикуется в интерфейсе, не пишется в
SQLite/activity и не может инициировать side effects. В подсказку попадают только
фиксированные инструкции, а не вставленный в system prompt пользовательский текст.
Нет универсального NLP-понимания сарказма, сложного косвенного отказа или любого языка.

Ответ соразмерен вопросу: нет обязательного вступления, плана, сочувствия или
предложения помощи. По умолчанию вопрос в конце не нужен; допускается один
вопрос при существенной неоднозначности. Можно спорить с аргументами и признавать
неопределённость. Это модель поведения основного вызова, без blacklist обычных
слов/приветствий и без автоматического обрезания всех вопросов.

Сохранён и уточнён отдельный guard неподтверждённых **утверждений о совершённом
сохранении/удалении/внешнем действии**: это проверка отсутствующего receipt, а не
запрет слов «забыл», «изменил», «сохранил». Объяснение работы памяти, цитаты и
рассказ о сохранённом файле проходят регрессии. Guard остаётся консервативной
эвристикой, не формальным доказательством истинности любого текста LLM.
Детерминированные подтверждения памяти создаются приложением только после commit.

## Контекст без смешивания с техническими статусами

Полный transcript хранится прежним способом и прежними privacy guards. В model
projection применяются лимиты 24 turns / 24 000 символов, без обрезания реплики
на середине предложения и без ведущего orphan assistant. Текущая реплика добавляется
ровно один раз; одинаковые реальные пользовательские сообщения не дедуплицируются.
Telegram update replay по-прежнему обслуживается прежним dedupe/cache протоколом.

Отдельно исключаются только **целые assistant records**, буквально равные
собственным transport/incomplete statuses приложения, включая legacy варианты
04/05. Пользовательский текст и обычные фразы с похожими словами не фильтруются.
Это совместимая проекция известных application statuses: прошлый сетевой отказ
не должен становиться образцом следующего содержательного ответа модели.
Исходные records не удаляются и не меняются. Если модель сама возвращает
целый собственный outage status приложения, ответ не считается успешной
генерацией и не разрешает автоматическое обновление памяти. В старой схеме нет отдельного outcome
столбца, поэтому распознавание старых статусов ограничено этим точным списком;
это явно протестированная граница совместимости, не semantic moderation.

`append_exchange` пишет обе реплики одной SQLite transaction через прежний
`_locked_transaction`. Ошибка INSERT assistant откатывает и user, не оставляя
половину пары. Память и transcript остаются разными операциями: этот PR не обещает
общую атомарность memory commit и последующей записи истории. Существующие
conversation locks сохраняются; глобальная многопроцессная сериализация всех
чатов этим изменением не вводилась.

В LLM попадают только релевантные confirmed memories прежнего участника после
прежнего sensitivity filter. Короткая отсылка может использовать предыдущую
пользовательскую тему; подтверждённое предпочтение формата ответа применяется
и без повторного упоминания «формат». Candidates не выдаются за подтверждённые
сведения. Не расширены memory eligibility, sensitive categories или доступы.
Нет новой миграции или изменения schema/checksums 05.1–05.4, recovery journal,
retention, tombstones, удаления и cross-user isolation.

## Надёжная HF-генерация

Спецификации: [HF Chat Completion](https://huggingface.co/docs/inference-providers/tasks/chat-completion),
[официальная карточка Qwen3-14B](https://huggingface.co/Qwen/Qwen3-14B).
HF возвращает finish reason и usage; Qwen поддерживает non-thinking mode.
Сохранён явный `enable_thinking=False` по умолчанию для HF; не предполагается,
что все совместимые провайдеры одинаково реализуют эту настройку.

Алгоритм:

1. Один обычный non-streaming text request; JSON shape/types проверяются, body
   ограничен 128 KiB, видимый текст — 32 000 символов. Empty/null/нестроковый content,
   tool/function calls, content filter и непригодные структуры отвергаются.
2. `reasoning_content` никогда не используется как ответ. Полные `<think>` blocks
   удаляются; незакрытые/неоднозначные blocks и служебные role tokens отвергаются.
   Неразмеченные рассуждения не всегда можно автоматически отличить от прозы.
3. `length`, исчерпанный budget при отсутствующем reason, незакрытый code fence
   или явно оборванная пунктуация активируют **не более одного** repair.
4. Repair — только текстовая генерация: verbatim prefix или проверяемый overlap,
   без tools, database access и повторного `respond()`. Бюджет repair —
   `min(2*T,2048)`. Неоднозначная склейка слов, повтор того же фрагмента или второй
   незавершённый ответ не выдаются как успех. Частичный ответ не пишется в историю.
5. HTTP 503/429, timeout и network errors не вызывают автоматический retry всего
   хода. Пользователь получает короткий понятный статус, без payload/секретов/
   traceback. Исходная реплика остаётся в диалоге; следующий ход может продолжить её.
   Ошибочная генерация не запускает автоматическое извлечение/обновление памяти.
6. Обе генерации делят deadline при запуске HTTP calls. Это **не жёсткий wall-clock
   cancellation**: DNS/TLS/сетевой стек urllib могут превысить ожидаемое время.
   В живом прогоне наблюдались turns >20 s при timeout 20 s. Ограничение числа
   попыток доказано, гарантированный SLA задержки не заявлен.

При отсутствии `finish_reason` с коротким видимым текстом сохраняется совместимость
с прежними OpenAI-compatible fixtures. `stop` с грамматически оборванным текстом
без структурных признаков не имеет надёжного локального детектора. Это ограничение
должно входить в дальнейшую качественную приёмку.

## Согласие и данные

Ни разговорный hint, ни модель не имеют экономического executor. Размышление,
чужая потребность, предложение ресурса, «да» без контекста и даже просьба
«переведи деньги» сами по себе не выполняют платёж/публикацию/передачу ресурса.
Существующие отдельные authenticated API flows с CSRF/access/confirmation
не менялись. Таблицы экономических операций проверяются после каждого сценария.
Необязательная activity telemetry не включалась. Новые диагностики содержат
типы/reason/usage, а не user text, keys, bearer headers или provider bodies.

Только синтетические реплики на временной общей pilot SQLite; запросы напрямую
к HF router `Qwen/Qwen3-14B:cheapest`, без production Space chat/API или настоящих

Секрет читается из существующего локального credential cache, не выводится и не

Контрольный старый прогон: 12 turns + отдельный pressure request с budget 96;
13 HTTP attempts, 5 transport timeouts, 8 received completions. Из них pressure
вернул `finish_reason=length`, а старый клиент выдал оборванное «гибкая метал»
как успех. Это реальный воспроизводимый дефект обработки результата.
[Полный synthetic before](validation06_1/hf-before.json).

Промежуточный after выявил контаминацию model context собственными статусами
сбоев: после успешных HTTP responses некоторые пользовательские ответы снова
были текстом недоступности. Причина отделяется от пустого content в последнем
tool instrumentation; неизвестные детали промежуточных payload не додумываются.
[Промежуточное evidence](validation06_1/hf-after-before-status-projection.json).
После этого добавлена совместимая projection статусов и повторена живая проверка.

[Заключительный after](validation06_1/hf-after.json): 12 turns и отдельный
pressure request, 13 HTTP attempts, **8 received completions / 5 transport
timeouts**, extraction calls 0. Четыре обычных turn и pressure не получили ответа.
Median turn 1426.885 ms, max 20840.93 ms; известный usage — 6719 input / 402
output tokens только для полученных completions. До изменения — median
2804.445 ms, max 28546.13 ms, известный usage 4673 / 869. Это разные успешные
подмножества; их нельзя выдавать за доказательство ускорения или удешевления.

Во всех восьми заключительных received completions content был непустым,
`finish_reason=stop`; ни один не совпал с собственным outage status. Все SQLite
integrity/FK/history/memory/economic invariants PASS. **Живой repair после
известного length в заключительном прогоне не проверен: pressure завершился
timeout.** Его работоспособность и ограничения подтверждают автоматические
негативные/integration tests. Реального HTTP 503 в этом повторе не было: 503
проверен негативными тестами, а реальные отказы здесь — transport timeouts.

[Ручная оценка по шести критериям](validation06_1/quality-review.json) оставляет
naturalness/no-repetition/intent acceptance открытыми. В заключительном after
снова появились приглашение продолжать после благодарности, слишком общая
реакция на размышление и необоснованный вывод о том, что рассказ о чужом
велосипеде облегчит чувства пользователя. Это реальные неудовлетворительные
ответы, а не пройденная качественная приёмка.

Из уже наблюдённых качественных различий: старый ответ на «Спасибо» —
«Пожалуйста! Если захочешь поговорить или узнать что-то ещё — я всегда рядом»;
в одном промежуточном after — «Пожалуйста.». Но в заключительном after снова
появилось «Если захочешь — продолжим разговор»; устойчивое улучшение этого
критерия **не доказано**. Чистая память-коррекция больше не заканчивается неполной
фразой «Казани»: подтверждение места жительства формируется после commit без
самодельного склонения названия города. При наличии содержательного вопроса
подтверждение не должно заменять весь ответ.

Критерии дальнейшей ручной приёмки: связность с последней репликой и предыдущей
темой; соразмерность и отсутствие заученных вступлений; отсутствие повторов и
необязательных вопросов; завершённость; уважение нового намерения/отказа;
нулевые нежелательные действия. Дополнительно нужна фактологическая проверка:
правдоподобный ответ на вопрос не считается доказанно правильным. Оценка автора
по синтетическим ответам не заменяет независимые пользовательские испытания.

## Токены, задержки и стоимость

Conversation classification: **0 дополнительных LLM calls**. Обычный ответ —
1 call. При известном обрыве — максимум 2; верхняя граница output budget —
`T + min(2*T,2048)` (по умолчанию 768+1536=2304). Это cap, не фактический расход.
Extraction памяти, как и раньше, добавляет максимум один отдельный call только
для прошедшей local gate устойчивой self assertion; его budget ограничен 384,
repair для JSON запрещён. На четырёх сценариях с полученными ответами в обоих запусках известный usage
составил input 2078→3080 и output 376→229 tokens. Это описательное сравнение
четырёх разных генераций, не доказанная экономия и не billing estimate.

Простые факты/прямые preference edits не требуют
отдельного extraction call. Сам existing основной call перед memory correction
сохранён ради совместимости failure semantics Foundation 04.

System instruction подробнее; history window вырос с 12 до 24 turns, но есть
24 000-character cap. Это может увеличить input tokens. Фактические usage и
latency каждого полученного ответа записаны в evidence; суммы usage относятся
только к полученным responses. При timeout запрос мог всё равно обрабатываться
провайдером: его billing/usage неизвестны. Сравнение median при разном количестве
отказов, вариативном `:cheapest` routing и малой выборке не доказывает ускорение.
Числовая стоимость в валюте не заявляется без тарифа конкретного route и billing
данных; ожидаемая стоимость определяется input/output usage и ценами провайдера.

## Оставшиеся ограничения и следующий шаг

1. HF доступность и фактическое качество не прошли приёмку. Транспортные таймауты,
   отдельные неудачные ответы и semantic truncation при ложном stop остаются рисками.
2. Классификация — hints, не универсальное понимание языка. 40 сценариев не
   покрывают весь сарказм, косвенные просьбы, культурные контексты и длительные беседы.
3. Service status projection точная, а не schema-level outcome metadata. Нужен
   отдельный reviewed design, если потребуется расширять provenance без эвристики.
4. Нет нового executor действий. Будущие tool calls потребуют отдельного consent
   state machine; естественное «да» не должно становиться разрешением автоматически.
5. Не сняты блокеры 05.4: реальная HF SQLite/volume attestation, независимые custody,
   replication/escrow, certified old-backup/legacy baseline, retention approval,
   реальные supported browsers/WebView/passkeys. CI не является pilot readiness.

Далее — ограниченные UX испытания с заранее заданными критериями, независимое
чтение ответов, проверка фактических ошибок, более стабильный HF route и наблюдение
bounded latency без логирования личных разговоров. До этих доказательств — без
объявления пилотной готовности или автоматического rollout.
